# closed 索引缓存到磁盘

closed 分区的扫描结果存在 `~/.pi/agent/session-panel/closed-cache.json`，下一次 pi 启动时先读它，再增量刷新。

## 为什么

本机 186 个真实会话文件一共 531 MB。`SessionManager.listAll()` 要把每个文件的每一行读出来拼 `allMessagesText`，全量跑一次 **1.5–1.8 秒**。面板打开时这段时间里 closed 分区是空的，用户看到的就是「要等一会儿才出来」。

增量之后：

| | 耗时 |
|---|---|
| 冷启动（无缓存） | ~1500 ms |
| 暖启动（每次 stat 187 个文件，只有目录里有变化才重扫） | ~11 ms |

## 怎么增量

每个缓存行带一个 `size:mtimeMs` 戳。扫描时：

1. 遍历会话目录，给每个文件取戳（155 ms → 实际 ~13ms，因为先按 sidecar 滤掉 1794 个 subagent 文件）。
2. 戳没变的行直接复用，不读文件。
3. 戳变了 / 新增了 / 删掉了的，它所在的**目录**交给 `SessionManager.listAll(dir)` 重扫。按目录而不是按整机，是因为 pi 的 API 只到目录这一级。
4. 重扫结果写回缓存，原子替换（tmp + rename）。

启动时有缓存就先画出来，扫描完成后替换。所以「打开就空着」变成了「打开就有，几毫秒后更新到最新」。

## Considered Options

- **只缓存不校验**：被否决。会话在 pi 外面被删、被改名，列表会一直显示幽灵行。
- **缓存全部 6.6 MB（含 `allMessagesText`）**：被否决。解析要 21ms，而且 5.8 MB 是搜索用的正文；搜索是低频操作，为它让每次启动都多花 20ms 不划算。现在缓存只存显示字段，正文在重扫时才有。
- **按文件而不是按目录增量**：被否决。pi 没有「只解析这一个文件」的公开 API，硬拆会复制它的解析逻辑。

## Consequences

缓存坏了、版本变了、agent 目录只读，都退回全量扫描——最坏等于没有缓存。

缓存里的行不参与 live 去重：`withoutLiveDuplicates` 在渲染时按当前注册表过滤，所以「缓存里是 closed、现在正在跑」的会话不会重复出现。

缓存的 `version` 必须跟着显示规则一起改。改了名字规则或过滤规则而不改 `CACHE_VERSION`，会有一代缓存带着旧结果。
